## Catch-up credits: what changed and what did not

`fairness.py` implements the service-deficit rule already argued in plan 18. This replaces the live coordinator's constant weight of one **only when the operator selects** `debt_weighted_surplus`. A new run still starts with `equal_surplus`. Credits accumulate under either rule so a later switch has a history.

For each interval, compute an equal-surplus reference with exact rational arithmetic. Credit change in Wh is `(reference total watts − conservative reserved member watts) × interval hours`, clipped to `[0,20]`. The same registered floor occurs in both totals and cancels. A member above its reference spends credit; a member below it earns credit. The weighted rule uses `1 + min(credit / 10, 1)`, so the weight stays in `[1,2]`. These are scenario parameters, not a calibrated household entitlement policy.

Inputs are captured before mutation, then integrated once with a monotonic clock. Intervals split at conservative reservation release, recovery end and offer/status expiry. A member needs a valid offer, matching member boot and recent online/at-floor status. Offer age limit is 3 seconds; status limit 1.5 seconds. A known partition, recovery, infeasible cap, stale/offline offer, invalid registered envelope or loop gap over 1.5 seconds freezes the relevant credit instead of inventing missing service. Stale/missing members retain their registered floors in the reference. Delayed offline detection is bounded by status freshness; it is not instant knowledge of a failed peer.

Credit is **withheld authorization**, not delivered energy, measured sacrifice or a deadline guarantee. The coordinator does not use member-supplied debt, meter consumption or private appliance lists to grant catch-up credit. An unused or undelivered grant still counts as possible authority until its conservative release. False useful demand inside a registered envelope remains a gaming opportunity; this does not make the mechanism strategy-proof. No automatic baseline punishment is added.

Persistence uses exact numerator/denominator pairs in the existing run SQLite database. It checkpoints before publishing every grant and during the half-second plan cycle. Restart restores the last committed credits and freezes unobserved downtime through the full recovery interval. A hard crash may lose an uncheckpointed accounting tail (normally up to a plan cycle, potentially longer under scheduling failure); it does not recompute or award that missing interval. This is an explicit relaxation of plan 18's ideal fully event-durable accounting, trading a small possible fairness loss for fewer synchronous disk writes. It cannot create authority or shorten a lease. Invalid persisted state disables weights for **all** members and exposes `corrupt_debt_state_weighting_disabled`; no reconnect race chooses a winner. It is not repaired by silently deleting the database.

Every emitted plan and lease Basis carries the actual rule, credit, weight and input hash. The hash now includes the rule and authoritative debt state. The allocator is weighted max-min on continuous **surplus for that fixed snapshot**; watt rounding rounds down. Changing weights/inputs and retained old leases still prevent a claim of instantaneous total-watt leximin or guaranteed eventual repayment.

## Exact additional HTTP contract

All paths below start `/api/v1`. Existing `/state`, WebSocket and cap/chaos semantics are preserved. The existing `Snapshot` shape is unchanged; `Operation.kind` adds `fault`. New `LabRequest` fields are optional with explicit defaults. Complete Pydantic input/output schemas are in `fixtures/openapi.json`.

Common live control body: `run_id:UUID`, `source:"live"`, `expected_control_revision:Nat`. Send `Idempotency-Key: UUID`. Cap/rule/chaos/fault share durable idempotency and revision checks; the same key cannot mean two different actions. A response of 202 acknowledges the recorded operation, not immediate electrical compliance.

| Endpoint | Request | Response |
|---|---|---|
| `POST /rule` | Common control fields + `rule:"equal_surplus"|"debt_weighted_surplus"` | 202 Operation, desired rule committed; coordinator adopts it on its next control read; old grants stay reserved. Corrupt debt gives 409 `debt_unavailable`. Mock returns 409 unsupported. |
| `GET /fairness` | None; live only | `FairnessView`: run_id, desired_rule, effective_rule, available, revision, error/null, scale_wh=10, maximum_wh=20, frozen_gap_ms, meaning, members[{member_id,debt_wh,weight}]. This reads the last durable checkpoint; the plan is the evidence of the rule actually used for a particular grant. |
| `POST /faults` | Common controls + target, action, duration_ms=8000, delay_ms=0, rate=1.0 | 202 durable Operation queued → applied/failed. Actions: partition, drop_acks, delay_telemetry, delay_grants. Duration 1–30000 ms; delay 0–10000 ms, positive only/always for delay actions; rate 0–1. |
| `GET /runtime` | None; live only | run_id; processes[{name,pid,running,exit_code/null}]; evidence_error/null; recording_full. No credentials, private paths or environment are returned. |
| `GET /operations/{id}` | Operation UUID | Now looks through durable history, including entries older than the 20-item visible Snapshot tail. |
| `GET /recordings` | None | RecordingCatalog: items[{recorded_run_id,bytes,replayable}], max_bytes, max_frames. Lists the configured live runtime root only; not arbitrary files. |
| `POST /replays` | `{recorded_run_id:UUID,from_seq:Nat=0,speed:1=1}` | 201 ReplayView, initially paused. A frozen copy of the available snapshot recording; 0 selects its first frame. No operator key/control revision is used. |
| `GET /replays/{id}` | Session UUID | ReplayView, advancing by recorded monotonic time only while playing. |
| `POST /replays/{id}/seek` | `{from_seq:Nat}` | ReplayView at exact stored frame sequence, paused. 0 selects first frame; gaps/out-of-range give 409. |
| `POST /replays/{id}/playback` | `{action:"play"|"pause"}` | ReplayView. Play runs at 1× recorded time; pause preserves position; playback stops at the end. Seek first to play from the beginning again. |
| `DELETE /replays/{id}` | None | `{deleted:true}` releases this in-memory session. Does not delete the recording. |
| `POST /lab/runs` | LabRequest below + `Idempotency-Key:UUID` | 202 LabJob + Location; no live control revision changes. GET Location to poll. Available live or mock. |
| `GET /lab/runs/{id}` | Job UUID | LabJob with running/complete/failed status, request, timestamps, result/null and error/null. |
| `POST /lab/benchmark` | Same LabRequest | Compatibility endpoint: awaits the same isolated worker and returns BenchmarkResult (200), or 429 busy / 503 failed. It no longer runs CPU-bound allocation in an API thread. |

Fault targets are `coordinator`, `member:member-a`…`member:member-e`, `plant:member-a`…`plant:member-e`, or `evidence`. `broker` is not a delivery-fault target; use existing broker kill/restart actions. `delay_grants` specifically targets a member. The target denotes that process's application send/receive fault shim, not a physical router or electrical fault. There is only one active delivery-fault file; applying a new fault replaces it. Existing buffered delayed messages still undergo ordinary identity/deadline checks after the fault expires. Retrying an idempotency key does not restart its duration. No automatic replay of a queued-on-crash process/fault action.

ReplayView fields: replay_id, recorded_run_id, sha256, gap, frame_seq, first_seq, last_seq, frame_count, playing, position_ms, duration_ms, snapshot. `snapshot` is the recorded complete Snapshot with source=`replay`, separate replay/stream IDs and view revision, empty operations and control capabilities disabled. Its `generated_at`, sample ages and metrics are historical values at that frame, not live wall-clock-aged observations. The original MQTT event_cursor is distinct from replay frame_seq. Poll replay at up to 4 Hz; the live WebSocket continues serving live/mock and is not switched by a replay operation.

LabRequest: `members:int 1..5000`, `seed:Nat`, `samples:int 1..200=200`, `distribution:"uniform"|"saturated"|"skewed"="uniform"`, `rule:Rule="equal_surplus"`, `cap_ratio:float 0..1=0.5`. Uniform draws useful limits 150–2000 W; saturated uses small identical 150 W limits; skewed uses 10000 W for every tenth synthetic member and 150 W otherwise. All floors are 100 W; cap_ratio selects the available fraction of aggregate surplus after floors. Weighted scenarios use seeded fixed weights, not a claim to simulate credit dynamics. The old hard-coded `members*500` cap is replaced by this declared ratio so scenario comparisons use the same definition.

BenchmarkResult retains members, seed, samples_ms, complete, median_ms, p95_ms, python, os, timer, scope, warmups, and adds distribution, rule, cap_ratio, validation_samples_ms, total_samples_ms, requested_samples. `samples_ms`/median/p95 remain **allocation only**. Matching indexed validation/total arrays separate independent validation cost. No MQTT, persistence, IPC, UI or appliance scheduler is included. Fixed device privacy means the planner does not iterate over private devices, but this endpoint does not claim to have benchmarked a per-device experiment. Member growth remains O(n log n).

Jobs allow one active child per API, retain the last 32 jobs and associated in-memory idempotency keys, and reject concurrent distinct jobs with 429. Duplicate keys return the current state of the same job; changed input gives 409. These computational job keys are **not** durable control keys; after server restart/eviction, submitting them may run a new benchmark. The worker receives scenario JSON and a minimal environment; it is application isolation, not a security sandbox. On Linux it is lowered in priority, pinned to one allowed CPU, and limited to 512 MiB address space and 12/13 seconds CPU. Parent wall timeout is 15 seconds, including warmup/startup; timed-out children are killed and reaped. One process still shares the physical PC's resources, so the full system has no real-time guarantee. The inner sampling loop may return a valid partial result (`complete=false`) before the outer deadline. A failed/killed job has no fabricated samples. API shutdown kills its active benchmark child.

## Recording and evidence limits

The observer writes a separate `snapshots.jsonl` at 2 Hz, capped at 32 MiB or 10000 frames. Reaching the cap stops that optional recording and sets runtime.recording_full; ordinary live MQTT observation and authority continue. Historical `events.jsonl` remains the raw wire evidence. Both contain privileged fictional demo details and remain ignored local artifacts. Old runs without snapshots are not retrospectively reconstructed into a made-up UI history.

Replay creation captures the bounded bytes once. Up to four sessions can exist. Later appends do not change a session's hash or frames. Gaps, truncated tails, malformed records, non-monotonic time/run/sequence and recorded observation gaps are visible; no interpolation fills missing electrical facts. Source files are never modified. Replayable in the catalog denotes file-size eligibility, not proof of complete or valid content; creation validates the data. A completed capped recording is a valid prefix, not a recording of what happened after its last frame.

Allocation timing is measured around registry/input validation, pure water-filling and independent proposal validation. Per-grant admission_ms measures ledger admission only, excluding SQLite commit, network and observation delay. Periodic summary plans leave admission_ms null because no grant was admitted by that summary. Stale plan timing becomes null in the live view. Do not sum these stage fields and call the result end-to-end latency.

Request bodies are bounded at 16 KiB even without Content-Length. Duplicate JSON keys, malformed/nonfinite JSON and invalid WebSocket pong shapes are rejected. The operator service still assumes the trusted local demo environment, loopback by default; no new production login/TLS or multi-host clock guarantee is implied.

Build order now: tested safety core → exact service-credit arithmetic → persisted rule control → live restart test; in parallel, bounded recorded snapshots → immutable seek/play/pause → frontend player; synthetic benchmark scenarios → isolated child lifecycle → live coexistence test → lab UI. Fault controls depend only on the existing tested fault shim and durable operation helper. No frontend module must exist for any backend acceptance test.

At 3 a.m.: choose equal_surplus if credit state is unavailable; preserve the database and full recovery wait. Reduce benchmark members/samples after a timeout. Delete replay sessions to free their slots; begin a new run if an old recording is capped and you need a new demonstration. Read `/runtime` before restarting any process. A stale UI or screen is not grounds to restart a healthy plant. The first remaining cuts are replay UI polish and extra benchmark scenarios, never protected floors or expiry checks.
